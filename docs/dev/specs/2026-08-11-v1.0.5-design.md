# v1.0.5 設計仕様

作成日: 2026-08-11

## 1. 目的

日本語・円に固定されているアプリを、日本以外のユーザーが使えるようにする。

1. **言語対応** — 画面の文言を日本語 / 英語 / 韓国語 / 中国語で切り替えられるようにする
2. **国設定** — 換算先を円固定でなく、住んでいる国の通貨にできるようにする

いまは UI 文言がすべて日本語のリテラルで、換算先も `toJpy` / `formatJpy` / `rateKey` の `JPY` として全層に埋まっている。ECB 参照レートは任意の通貨ペアを返せるので、換算先を持ち回せる形にすれば為替の仕組み自体は変えずに済む。

## 2. スコープ

### 含むもの

- 日本語 / 英語 / 韓国語 / 中国語の 4 言語。初期値は端末の言語から推定、設定で上書き
- 旅行ごとの換算先通貨(`Trip.homeCurrency`)。アプリの設定は「新しい旅行の既定値」だけを決める
- 対応通貨を 9 → 30(Frankfurter が返す全通貨)に拡張し、国旗付きのリストから選ばせる
- レート取得・キャッシュ・バックアップ・集計の「円」を換算先通貨に一般化する
- DB スキーマ v3 とバックアップ形式 v3 への移行
- 上記に伴うテストの追加・更新、README とバージョンの更新

### 含まないもの

- 既存の旅行の換算先の変更。移行時は全部 JPY にし、支出が 1 件でもある旅行は換算先を変えられない(レートを支出に焼き付けているため。第 4 節)
- 通貨名の翻訳。`Intl.DisplayNames` に任せる(第 5 節)
- 日付の並びと数値の区切り記号のロケール対応。日付は 4 言語とも `9/12(土)` の形のまま(曜日名だけ訳す)、数値は 4 言語とも 3 桁区切りのカンマ + ピリオド小数で揃うので、既存の自前フォーマッタを使い続ける
- 右横書き(RTL)言語、複数形の変化(4 言語とも不要)
- 翻訳ファイルの外部化(JSON / PO)や i18n ライブラリの導入。依存を増やさない
- 言語ごとの `lang` 属性の切り替え以上の SEO / アクセシビリティ対応
- 通貨ごとの入力桁数の自動調整以上の入力 UI 変更

## 3. 用語

| 語 | 意味 |
|---|---|
| 現地通貨(`Trip.currency`) | 旅行先で支払う通貨。支出の入力単位 |
| 換算先通貨(`Trip.homeCurrency`) | 合計・予算・グラフを表示する通貨。従来の「円」 |
| レート | 「1 現地通貨 = ? 換算先通貨」。支出に焼き付けて再計算しない |

コードでは換算先を `home` と呼び、`Jpy` という語は使わない。

## 4. データモデル

### Trip

```ts
export type Trip = {
  id: string;
  name: string;
  /** 現地通貨。ISO 4217。"CNY" など */
  currency: string;
  /** 現地通貨の最小単位の桁数 */
  currencyDecimals: number;
  /** 換算先通貨。ISO 4217。"JPY" など */
  homeCurrency: string;
  /** 換算先通貨の最小単位の桁数 */
  homeCurrencyDecimals: number;
  startDate: string;
  endDate: string | null;
  /** 個別支出の予算(換算先通貨の最小単位)。未設定は null */
  personalBudgetHome: number | null;
  /** 共有支出のうち自分の負担分の予算。未設定は null */
  sharedBudgetHome: number | null;
  memberCount: number;
  createdAt: number;
};
```

`homeCurrencyDecimals` を持たせるのは `currencyDecimals` と同じ理由で、通貨マスタから引き直さずに済ませるため。旅行を作った後にマスタの桁数を変えても、既存の旅行の金額の意味が変わらない。

**換算先は旅行ごとに持つ。** アプリ 1 つに 1 個だけ持つと、あとから換算先を変えたときに過去の支出の焼き付けレートが別の通貨に対するレートのまま残り、合計が意味を失う。旅行ごとなら「支出が 1 件でもあれば変えられない」というロックだけで整合性が保てる(現地通貨がすでにそうしている)。

**既存データの予算はそのまま使える。** JPY は最小単位の桁数が 0 なので、`personalBudgetJpy: 50000`(円)は `personalBudgetHome: 50000`(JPY の最小単位)と同じ値。移行はフィールド名の変更だけで、値の変換は要らない。

### Expense

変更なし。`rate` は「1 現地通貨 = ? 換算先通貨」の意味になるが、旅行ごとに換算先が固定でロックされるので型も値も変わらない。

### RateCache

```ts
export type RateCache = {
  /** "CNY:JPY:2026-09-12" */
  key: string;
  base: string;
  /** 換算先。"JPY" など */
  quote: string;
  date: string;
  rate: number;
  effectiveDate: string;
  fetchedAt: number;
  source: 'frankfurter' | 'er-api';
};
```

`key` の形式は現状すでに `${base}:${quote}:${date}` なので変えない。`quote` をフィールドとして立てるのは、オフライン時のフォールバック(`latestCachedRate`)が通貨ペア単位で引けるようにするため。

### RateSource

```ts
export type RateSource = 'api' | 'cache' | 'manual' | 'same';
```

現地通貨と換算先通貨が同じとき用に `'same'` を足す。第 6 節。

### DB スキーマ v3

```ts
this.version(3)
  .stores({
    rates: 'key, base, quote, [base+quote], [base+date], date',
  })
  .upgrade(async (tx) => {
    await tx.table('trips').toCollection().modify((trip: Record<string, unknown>) => {
      Object.assign(trip, migrateTrip(trip));
      delete trip.budgetJpy;
      delete trip.personalBudgetJpy;
      delete trip.sharedBudgetJpy;
    });
    await tx.table('rates').toCollection().modify((r: Record<string, unknown>) => {
      r.quote = 'JPY';
    });
  });
```

`trips` はインデックス対象のフィールドを増やさないので `stores` に出さない(v2 と同じ流儀)。`rates` は `[base+quote]` を足すので `stores` に出す。Dexie は `version(3).stores()` に書いたテーブルだけを再定義するので、他のテーブルの定義は v1 のものが引き継がれる。

`migrateTrip` は `migrateTripBudget` を改名・拡張したもので、DB の upgrade とバックアップ取り込みの両方から呼ぶ。IndexedDB に依存させない方針は据え置き。

```ts
/** v1(budgetJpy)・v2(personalBudgetJpy)・v3 のどの形の旅行も v3 形式に直す。 */
export function migrateTrip(trip: Record<string, unknown>): Trip;
```

やること:

1. `budgetJpy` があり `personalBudgetJpy` が無ければ `personalBudgetJpy` に移す(既存の挙動)
2. `personalBudgetJpy` / `sharedBudgetJpy` を `personalBudgetHome` / `sharedBudgetHome` に改名する
3. `homeCurrency` が無ければ `'JPY'`、`homeCurrencyDecimals` が無ければ `0` を入れる
4. 旧フィールド(`budgetJpy` / `personalBudgetJpy` / `sharedBudgetJpy`)を消す

すでに v3 形式なら 1〜4 はどれも何もしない。

### バックアップ形式 v3

`BackupFile.version` を 3 にする。`parseBackup` は 1 / 2 / 3 を受け入れ、旅行を `migrateTrip` に通してから返す。`isTrip` の予算チェックは新旧どちらのフィールド名でも通るよう `isBudgetField` を 4 つのキーに広げ、`homeCurrency` は「無いか文字列」を許す(v1 / v2 のファイルには無いため)。

古いバージョンのアプリが v3 のファイルを取り込もうとすると「対応していないバージョンです: 3」で弾かれる。これは意図した挙動。

`parseBackup` の日本語エラー文字列は言語を選べなくなるので、コードに変える。

```ts
export type BackupErrorCode = 'invalid-json' | 'not-backup' | 'unsupported-version' | 'broken';

export class BackupError extends Error {
  constructor(readonly code: BackupErrorCode, readonly detail?: string) { super(code); }
}
```

`SettingsScreen` が `err instanceof BackupError ? t.backup.error[err.code](err.detail) : t.backup.error.unknown` の形で文言に変える。

```ts
/** 通貨のその言語での名前。"米ドル" / "US Dollar" / "미국 달러" / "美元" */
export function currencyName(code: string, lang: Lang): string {

```

`Intl.DisplayNames` は iOS 14.1 以降 / Chrome 81 以降で使え、このアプリの対象(PWA として動く現行ブラウザ)を満たす。無い環境ではコードをそのまま出す。

補足:

- **HUF と IDR は ISO 4217 では 2 桁だが 0 桁にする。** どちらも実際の支払いで小数を使わず、2 桁にすると 1 件ごとにゼロを 2 つ余計に打つことになる。集計の丸め誤差は 1 ルピア / 1 フォリント未満なので実害がない

## 6. 為替

### resolveRate

```ts
export async function resolveRate(
  base: string,
  quote: string,
  date: string,
  overrides: Partial<ResolveRateDeps> = {},
): Promise<ResolvedRate | null>;
```

`ResolveRateDeps` の各関数も `quote` を取る形に揃える。依存注入でテストする方針は据え置き。

```ts
export type ResolveRateDeps = {
  getCachedRate: (base: string, quote: string, date: string) => Promise<RateCache | undefined>;
  putCachedRate: (entry: RateCache) => Promise<void>;
  latestCachedRate: (base: string, quote: string) => Promise<RateCache | undefined>;
  fetchFrankfurter: (base: string, quote: string, date: string) => Promise<FetchedRate>;
  fetchErApi: (base: string, quote: string, fallbackDate: string) => Promise<FetchedRate>;
  today: string;
};
```

**`base === quote` を先頭で短絡する。**

```ts
if (base === quote) {
  return { rate: 1, effectiveDate: date, source: 'same', stale: false };
}
```

換算先が選べるようになると「日本国内の旅行を JPY で記録する」が普通に起こる。Frankfurter に `?base=USD&symbols=USD` を投げると `{"message":"bad currency pair"}` が返り、フォールバックまで一巡して最後に手動入力を求める羽目になる。キャッシュにも書かない(意味のない行が溜まるだけ)。

`rateKey` / `getCachedRate` / `latestCachedRate` も `quote` を取る。

```ts
export function rateKey(base: string, quote: string, date: string): string {
  return `${base}:${quote}:${date}`;
}
```

`latestCachedRate` は `db.rates.where('[base+quote]').equals([base, quote])` で引く。通貨ペアを跨いだフォールバックはしない(USD→JPY のレートを USD→KRW に使ったら大惨事なので)。

### 小さいレートの精度

換算先が JPY のときレートは必ず 0.1 以上だったが、任意のペアになると `IDR → USD = 0.000056` のような値が出る。両プロバイダとも**結果を丸めて返す**ので、そのままでは有効数字が 2 桁しか残らず最大 0.9% ずれる。

**Frankfurter — 常に `amount=1000000` を付けて 1e6 で割る。**

```
GET /v1/2026-08-08?base=IDR&symbols=USD&amount=1000000
→ { "rates": { "USD": 56.306 } }  → rate = 5.6306e-05
```

`amount` は元の要求に乗るだけなのでリクエストは増えない。JPY 側でも精度が上がるだけで害はない(`USD→JPY` は `158641281` → `158.641281`)。

**er-api — `amount` が無いので、小さすぎるときだけ逆を引く。**

```ts
const direct = json.rates?.[quote];
if (direct < 0.1) {
  // latest/<quote> を引いて 1 / rates[base] を使う。失敗したら direct のまま
}
```

2 回目が落ちたら `direct` を使う。er-api はそもそも Frankfurter が落ちたときの当日レート限定のフォールバックなので、精度より値が返ることを優先する。

## 7. 金額の表示

`src/domain/money.ts`:

```ts
/** 現地通貨の最小単位を換算先通貨の最小単位に換算する。換算はこの関数だけを通す。 */
export function toHomeMinor(
  amountMinor: number,
  decimals: number,
  rate: number,
  homeDecimals: number,
): number {
  return Math.round(minorToMajor(amountMinor, decimals) * rate * 10 ** homeDecimals);
}

/** 通貨記号を添えた表示。"¥5,116" / "$34.20" / "1,234元"。記号の位置は通貨マスタの symbolAfter に従う。 */
export function formatWithCurrency(amountMinor: number, currency: string): string;
```

**`formatJpy` は消し、`formatWithCurrency` 1 本にする。** 換算先専用の `formatHome` を別に作ると `formatWithCurrency(x, trip.homeCurrency)` と同じ中身の関数が 2 つ並ぶだけになる。呼び出し側は現地通貨なら `trip.currency`、換算先なら `trip.homeCurrency` を渡す。

桁数の出どころは既存の流儀を守る。**計算は旅行に保存した桁数、表示は通貨マスタの桁数**を使う(いまも `expenseJpy` は `trip.currencyDecimals`、`formatWithCurrency` は `currencyDecimals(code)` を見ている)。表示側をマスタ由来にしておけば、金額しか持たない表示部品(`CategoryChart` / `DailyChart`)に通貨コード 1 つを渡すだけで済む。

`toHomeMinor` に `homeDecimals` が要るのは、換算結果を「換算先通貨の最小単位」に揃えるため。JPY(0 桁)なら従来どおり `Math.round(major * rate)` と同じ値になり、既存の数字は変わらない。

`group()`(3 桁区切り)はそのまま使う。4 言語ともカンマ区切り・ピリオド小数なので分ける理由がない。

`formatWithCurrency` には 2 か所直しが要る。

- `currency === 'CNY'` の直書きを `findCurrency(currency)?.symbolAfter` に置き換える
- **負の符号を記号の外に出す。** いまの `formatWithCurrency` は `formatMajor` の返り値(`-1,200`)に記号を足すので `¥-1,200` になる。`formatJpy` は `-¥1,200` を返していた。予算の残額はマイナスになりうるので、`formatJpy` 側の形に揃える。後置の通貨は `-1,200元`

`formatMajor` 自体は変えない(外貨の入力欄で使っており、そちらは符号の位置の問題がない)。

## 8. i18n

### 構成

```
src/i18n/
  ja.ts        辞書の原本。型の定義元
  en.ts        const en: Dictionary = { ... }
  ko.ts        同上
  zh.ts        同上
  index.ts     Lang / Dictionary / DICTIONARIES / detectLang
  LangContext.tsx   Provider と useI18n
```

```ts
// index.ts
export type Lang = 'ja' | 'en' | 'ko' | 'zh';
export type Dictionary = typeof ja;
export const LANGS: { value: Lang; label: string }[] = [
  { value: 'ja', label: '日本語' },
  { value: 'en', label: 'English' },
  { value: 'ko', label: '한국어' },
  { value: 'zh', label: '中文' },
];
export const DICTIONARIES: Record<Lang, Dictionary> = { ja, en, ko, zh };
```

言語名は自称(endonym)で出す。設定画面で自分の言語を探せるようにするため、現在の言語に関わらず固定。

### 辞書の形

素の入れ子オブジェクト。値は文字列か、引数を取る関数。

```ts
// ja.ts
export const ja = {
  weekdays: ['日', '月', '火', '水', '木', '金', '土'],
  category: { food: '食事', transport: '交通', /* ... */ },
  home: {
    total: '合計',
    sharedPerPerson: (n: number) => `自分の負担(${n}人)`,
    budget: (label: string, budget: string, rest: string) => `${label} ${budget} / 残り ${rest}`,
  },
  trip: {
    personalBudget: (code: string) => `個別予算(${code})`,
  },
  // ...
} as const;
```

`t('home.total')` 形式の文字列キーではなく `t.home.total` にする理由:

- `const en: Dictionary = { ... }` と書くだけで、キーの抜け・余分・引数の数と型の食い違いが `tsc --noEmit`(= `npm run lint`)で全部落ちる
- 韓国語・中国語は目視レビューできない。**型検査で捕まえられる範囲を最大にする**のがこの設計の主目的
- キー文字列のパースも補完用の型パズルも要らない

`as const` を付けるのは `ja` 側だけ。他の 3 つは `Dictionary` 型注釈で受ける。

### 初期値の推定

```ts
/** 端末の言語から表示言語を推定する。分からなければ英語。 */
export function detectLang(tags: readonly string[] = navigator.languages ?? []): Lang;

/** 表示言語から換算先通貨の既定を決める。 */
export function defaultHomeCurrency(lang: Lang): string;
```

`detectLang` は渡されたタグを順に見て、先頭 2 文字(小文字化)が `ja` / `en` / `ko` / `zh` のどれかに一致した最初のものを返す。1 つも一致しなければ `en`。既定の引数は `navigator.languages`(空や未定義なら `[navigator.language]`)。`zh-Hant` / `zh-TW` も `zh` に寄せる(簡体字の 1 種類だけを持つ。繁体字の作り分けはしない)。

`defaultHomeCurrency` は `ja → JPY` / `en → USD` / `ko → KRW` / `zh → CNY`。あくまで初期値で、設定でいつでも変えられる。

### 設定の保存

### 配り方

```tsx
// LangContext.tsx
export function LangProvider({ children }: { children: ReactNode }): JSX.Element;
export function useI18n(): { lang: Lang; t: Dictionary; setLang: (l: Lang) => void };
```

`LangProvider` は初回に `loadLang() ?? detectLang()` で決め、`setLang` で state を更新して `saveLang` する。`document.documentElement.lang` も合わせて書き換える。`App` の一番外側(`ErrorBoundary` の内側)に置く。

言語は画面の再読み込みなしで切り替わる。React の state なので、`useI18n` を使うすべての部品が再描画される。

### 辞書に移すもの

| いまの場所 | 移す先 |
|---|---|
| UI の日本語リテラル(約 80 か所) | 画面ごとの入れ子(`t.home.*` / `t.summary.*` / `t.trip.*` / `t.settings.*` / `t.expense.*` / `t.common.*`) |
| `date.ts` の `WEEKDAYS` | `t.weekdays` |
| `categories.ts` の `label`(カテゴリ / 支払方法 / 個別・共有) | `t.category.*` / `t.payment.*` / `t.scope.*` |
| `backup.ts` のエラー文字列 | `t.backup.error.*`(第 4 節のコード経由) |

`CATEGORIES` / `PAYMENTS` / `SCOPES` は `value` / `icon` / `color` だけを持つ配列に痩せる。`categoryLabel(v, t)` のように辞書を引数で受ける形にして、`categories.ts` から i18n への import を作らない。

`formatDateLabel` も同じ理由で `formatDateLabel(isoDate, weekdays)` にする。`date.ts` は純粋な日付関数のままにしておきたいので、モジュール内に「現在の言語」を持たせない。

ソース中の**コメント**は日本語のままにする。読者は開発者(日本語話者)で、翻訳対象ではない。

## 9. 画面

### 設定

「旅行」の上に「表示」セクションを足す。

```
表示
  言語        [日本語 ▾]
  換算先通貨   [🇯🇵 JPY — 日本円 ▾]
  ここで選んだ通貨は新しい旅行の初期値です。旅行ごとの換算先は各旅行の編集から変えられます。
```

補足文を必ず出す。ここを変えても既存の旅行の表示が変わらないのは分かりにくいので、明示する。

### 旅行の追加・編集

通貨の下に換算先通貨を足す。どちらも国旗付きの `<select>` で、表示は `🇺🇸 USD — 米ドル`(旗 + コード + `currencyName`)。国名ではなく通貨で選ばせるのは、ユーロのように 1 通貨が複数国にまたがる場合に国リストだと破綻するため。

```
通貨        [🇨🇳 CNY — 中国人民元 ▾]   ← 支出があるとロック(既存)
換算先通貨   [🇯🇵 JPY — 日本円 ▾]      ← 支出があるとロック(新規)
個別予算(JPY)
共有予算(JPY・自分の負担分)
```

換算先のロックは現地通貨と同じ `expenseCount > 0` を条件にし、同じ文言(`t.trip.lockedByExpenses`)を出す。予算のラベルは `homeCurrency` のコードを差し込み、選択を変えたら即座に追随する。

予算の入力欄は「換算先通貨の主単位」で書かせ、保存時に最小単位へ直す。`parseBudget` を捨てて `parseMajorToMinor(text, currencyDecimals(homeCurrency))` を使い、空欄なら `null`、負なら 0 に丸める。初期値は逆に `formatMajor(value, decimals)` から `,` を除いた文字列にする。0 桁の通貨(JPY / KRW)はいままでと同じ整数入力、2 桁の通貨(USD / EUR)は `1500.50` のように小数 2 桁まで受け付ける。桁数はマスタ由来にする(第 7 節の「表示はマスタ」に揃える。フォームは保存前なので `trip.homeCurrencyDecimals` はまだ確定していない)。

新規作成時の初期値は `loadHomeCurrency() ?? defaultHomeCurrency(lang)`。

### 支出の入力

- 換算プレビュー `¥2,816` は `formatWithCurrency(x, trip.homeCurrency)` を通すので自動で追随する
- レートの行 `1元 = ? 円` は `t.expense.rateLabel(fromSymbol, toSymbol)` にする
- **現地通貨と換算先通貨が同じとき(`source === 'same'`)はレートの行と換算プレビューを両方隠す。** `1¥ = 1 ¥` と `¥1,200 → ¥1,200` を出しても情報がない

### ホーム・集計

文言を辞書に差し替え、`formatJpy(x)` を `formatWithCurrency(x, trip.homeCurrency)` に置き換える。`CategoryChart` / `DailyChart` は計算済みの値だけを受け取る表示部品(v1.0.4)なので `trip` は渡さず、`homeCurrency: string` を props に 1 つ足すだけにする(`useI18n` は部品の中で直接呼ぶ)。

`summary.ts` のフィールドは全部 `*Jpy` → `*Home` に改名する。`totalJpy` / `personalJpy` / `sharedJpy` / `sharedPerPersonJpy` / `myTotalJpy` / `personalBudgetJpy` / `personalRemainingJpy` / `sharedBudgetJpy` / `sharedRemainingJpy` / `CategoryBreakdown.jpy` / `DailyPoint.jpy` / `DailySeries.totalJpy` / `maxJpy` / `averageJpy` / `DateGroup.jpy`、関数は `expenseJpy` → `expenseHome`、`myShareJpy` → `myShareHome`、`viewJpy` → `viewHome`。`data-testid` の `total-jpy` などは `total-home` に揃える。

行ごとに丸めてから足す方針(v1.0.4)はそのまま。

## 13. 手動確認

実機で次を確認する。

- 端末の言語が日本語なら日本語、英語なら英語で起動する
- 設定で言語を切り替えると、再読み込みせずに画面全体の文言が変わる
- アプリを開き直しても選んだ言語が残っている
- 4 言語すべてでボタンやラベルがはみ出さず、レイアウトが崩れない
- 設定の換算先通貨を USD にして新しい旅行を作ると、換算先の初期値が USD になっている
- 既存の旅行(移行後)の換算先が JPY になっていて、金額が v1.0.4 と同じ
- 支出のある旅行では換算先通貨が選べず、ロックの説明が出る
- 現地通貨 CNY / 換算先 USD の旅行で支出を記録でき、レートが `1元 = 0.14$` のように出る
- 現地通貨と換算先が同じ旅行(JPY / JPY)で、レートの行と換算プレビューが出ず、そのまま保存できる
- 換算先が USD の旅行で予算に `1500.50` を入れて保存し、残額が `$1,472.42` のように小数 2 桁で出る
- IDR / HUF の旅行で金額を小数なしで入力できる
- 機内モード(オフライン)にしても、キャッシュ済みの通貨ペアなら換算が出る
- v1.0.4 で書き出したバックアップを取り込むと、旅行の換算先が JPY になり金額が変わらない
- v1.0.5 で書き出したバックアップを別のブラウザで取り込める
- 壊れた JSON を取り込むと、選んでいる言語でエラーが出る

## 14. リスク

- **韓国語・中国語の訳文を目視で検証できない。** 型検査でキーの抜けと引数の食い違いは防げるが、訳の質は担保できない。`ko.ts` / `zh.ts` は 1 ファイルに閉じ、後から差し替えやすくしておく。README にも「ko / zh は未レビュー」と書く
- **改名の範囲が広い。** `*Jpy` → `*Home` はソースのほぼ全ファイルに触る。`tsc --noEmit` が全部拾うので、実装は「型が通るまで直す」で進められるが、途中でコミットを分けにくい。第 12 節の順序を守って段階ごとに `npm run lint` を通す
- **`Intl.DisplayNames` の訳語はブラウザ任せ。** 環境によって「米ドル」「アメリカ合衆国ドル」のように揺れる。コードと旗を必ず併記するので、通貨の取り違えは起きない
- **er-api の逆引きでリクエストが 2 倍になる場合がある。** 小さいレート(0.1 未満)かつ Frankfurter が落ちているときだけなので、実際に起きる頻度は低い
